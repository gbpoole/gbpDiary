name: calendar-import
description: Read before working on macOS Calendar / EventKit meeting import — CalendarService, CalendarEventImport, AttendeeMatcher, and the resolve(granted:) first-grant "approve-then-empty" gotcha.
---

**Import a meeting from the macOS Calendar (macOS only).** The diary add-meeting flow is unchanged (`ActivitySection.addMeeting()` → `MinutesDetailView(asSheet:true, isNew:true)`). For a **new** meeting, `MinutesDetailView`'s metadata block gains an **"Import"** row that is a standard `FuzzyPickerField` (single-select over the day's calendar events) — the same search/filter picker used for projects/people. Per-calendar filtering is expressed as **filter chips** (one per calendar with events in the window; none active → all shown), and the options are ordered by **closeness to the meeting's own `meetingAt`** (`CalendarEventImport.sortedByProximity`) — not to `now`, which buried the events of the day you were reviewing under today's. The picker spans a **multi-day window** (currently ±3 days, bounds from `CalendarEventImport.importWindow`) rather than a single day, so you can import an event from a nearby day (catching up the next morning, or a recurring event that only lands on certain weekdays — EventKit expands recurrences within the queried range). Since `addMeeting()` stamps a new meeting on the **viewed diary day**, that window alone hides today's events whenever you are reviewing another day, so the query uses **`CalendarEventImport.importWindows(around:now:…)`** — the anchor's window plus today's when `now` sits outside it (merged when they touch) — fetched through `CalendarService.events(inWindows:refreshingSources:)`, which dedupes by event id. Each option's label shows the **day + time** (`importEventLabel`) since results span several days. Picking an event calls `applyImportedEvent` → sets summary/time/duration and resolves attendees: matched People are added; **unmatched attendees are NOT auto-created** — they appear as **yellow "Unrecognized" chips** (`AppTheme.warning`) that the user clicks to reconcile via `ResolveAttendeeSheet` (segmented "Existing person" → link and add the scraped email to that Person's list, or "New person" → name prefilled + optional institution). Unresolved flags are session-only (ephemeral `@State`); confirming the meeting with any still pending prompts a confirm alert (they're then dropped). Loading lives in **`.task(id: minutes.meetingAt)`** (new meetings only), so re-dating the meeting re-queries and the work can wait on EventKit; the access request is bridged to async with `withCheckedContinuation`. If denied, the row shows an "Enable calendar access…" button linking to System Settings. **Two EventKit lifetime rules, both learned from "the list regularly comes up empty":** (1) there is exactly **one store for the app** — `CalendarService.shared`, read by `MinutesDetailView` and `CalendarSettingsView` as a plain `let`. `@State private var service = CalendarService()` constructs a new `EKEventStore` on *every* struct init and keeps whichever one mounted; a store loads its sources (local, CalDAV, Exchange) lazily, so a fresh one answers its first query with **no events and no error**. (2) because an empty result is therefore ambiguous, `loadCalendarEvents` **retries up to 4 times, 300ms apart, refreshing the sources on the first attempt** (`refreshSourcesIfNecessary()`), and stops early if the sleep throws (the task was cancelled). **RULE: never construct a `CalendarService`/`EKEventStore` per view, and never treat one empty EventKit fetch as "no events".** A long-lived store brings its own requirement: each refreshing fetch calls **`store.reset()`** before `refreshSourcesIfNecessary()`, because an un-reset store keeps serving its cached snapshot and can answer with nothing after Calendar syncs (constant with Exchange/CalDAV) — drafts are copied out immediately, so invalidating its objects is free. **And because an empty fetch is indistinguishable from an empty stretch of calendar, the app says which it was instead of leaving a blank picker:** every load records `CalendarImportDiagnostics` (`Domain/CalendarImportDiagnostics.swift` — access, the days actually queried, events, calendars, attempts), `summary()` renders it as the caption under an empty picker and into the log via `CalendarImportLog.record`, and a **Retry** button bumps `CalendarLoadKey.attempt` to re-run the load. This was added after the empty-list cause was diagnosed twice from reading code and was wrong both times — **diagnose this one from the caption or the log, not from a theory** (`log show --predicate 'subsystem == "io.github.gbpoole.gbpDiary"' --last 1h`). **On first grant the resolved access is taken from EventKit's `granted` flag, not a re-read of `authorizationStatus`** (`CalendarService.resolve(granted:fallback:)`, pure/tested): right after approval TCC hasn't propagated the new status, so re-reading it would report `.notDetermined` and the picker would never load — the reported "approve, then the list stays empty" bug. `resolve` returns `.authorized` when `granted`, else the read status (to distinguish denied/restricted/writeOnly). **EventKit is confined to `CalendarService`** (`Domain/CalendarService.swift`, `#if os(macOS)`): it requests access via the completion-handler API (not `async`, since `Swift.Task` is shadowed here), reads events across all calendars — which already aggregate Exchange + Gmail/CalDAV accounts registered on the Mac — and maps `EKEvent`s to platform-neutral `CalendarEventDraft`s (tagged with their `calendarId`/`calendarTitle`). The pure, testable logic lives in `Domain/CalendarEventImport.swift` (Foundation only; no EventKit/SwiftData): `minutesDraft(from:)` maps title→summary/start→meetingAt/(end−start)→duration, `sortedByProximity(_:to:)` orders by distance from a reference time, `displayName(fromEmail:)` derives a human name from an email local part ("john.smith@x.com" → "John Smith"; used when an invite has no display name), and `AttendeeMatcher.resolve(...)` matches attendees to existing People by **any email in the Person's ordered `emails` list** (case-insensitive) then name (the rest become `.create` intents the UI flags for reconciliation). `ResolveAttendeeSheet` follows the app's edit-modal style (ScrollView + GroupBox sections, rounded-border name field, styled header) and uses a `FuzzyPickerField` for the institution — which can **create a new institution** inline. Requires the `com.apple.security.personal-information.calendars` entitlement (`gbpDiary/gbpDiary.entitlements`) and the `NSCalendars*UsageDescription` Info.plist strings.
